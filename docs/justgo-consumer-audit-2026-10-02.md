# JustGo consumer product audit — 2 October 2026

## Scope and confidence

This is a static audit of the current `Meridian-Mobile` JustGo product, the shared `Meridian` backend, the public JustGo site, and the creator console. The mobile checkout contains uncommitted work, so findings describe the files on this laptop on 2 October, not a confirmed store release. I did not inspect a signed app on a device, production analytics, conversion rates, or live city inventory. Severity reflects likely user impact; it is not a measured loss estimate.

The product has meaningful foundations already: a personalized weekly Drop, Explore/search/agenda, event sharing and public pages with server generated social metadata, interested/registered plans, friends and crews, calendar add, weekly push, safety controls, and creator analytics. The [product strategy](../../Meridian-Mintlify/strategy/just-go-drop-ranker-vision.mdx) explicitly makes the Drop the main discovery surface and Explore a secondary browse/search surface. The recommendations below preserve that shape.

## Competitive reference points

| Product | Current consumer convention relevant to JustGo |

| [Partiful](https://help.partiful.com/en-us/articles/15525594-why-use-partiful) | Shareable event page, guest RSVP without an app, reminders, guest list visibility, host updates, and post-event photos. Its newer [Explore](https://help.partiful.com/en-us/articles/15525568-what-is-the-partiful-explore-page) combines local events with friend activity, and its [public Explore page](https://partiful.com/explore) exposes city events on the web. |
| [DICE](https://dice.fm/bundle/dooinit-festival-4mwr?lng=en-US) | Personalized event discovery, artist follows, upfront price, saved events, sharing, and ticket management. | [Fever](https://feverup.com/en) | City-first public discovery across categories with search and filtering, plus prominent access to support. |

These are product comparisons, not claims that every competitor capability should be copied. The common baseline is a confident route from discovery to a real plan: find an event, assess cost and constraints, save it, complete registration, retrieve proof, get updates, and arrive.

## Ranked findings

### P0 — repair the discovery-to-attendance path

**1. Public event CTA can point to the page the visitor is already on.** In [`JustGoPublicEvent.jsx`](../frontend/src/pages/JustGoPublicEvent/JustGoPublicEvent.jsx), the primary action for an actionable event links to `event.canonicalUrl`; the public contract makes that URL `https://justgo.lol/events/:id`. On the JustGo event page, this is a same-domain self-link. [Apple documents](https://developer.apple.com/documentation/technotes/tn3155-debugging-universal-links) that Safari keeps same-domain universal links in the browser. The “register/open app” CTA can therefore reload the page for an iPhone visitor rather than open the installed app. It also provides no registration path to someone without the app. **Action:** give the page a distinct, tested app-open handoff (a properly associated different subdomain or explicit scheme with fallback), then provide a direct external registration action when the event has an external link. Test installed/uninstalled states in Safari, in-app browsers, Android Chrome, and desktop. Track app-open success separately from taps.

**2. “Going” is self-reported after leaving for an external ticket site.** [`usePivotRegisterFlow.ts`](../../Meridian-Mobile/src/pivot/hooks/usePivotRegisterFlow.ts) opens the external URL and then asks whether the person got a ticket; [`PivotEventDetailScreen.tsx`](../../Meridian-Mobile/src/pivot/screens/PivotEventDetailScreen.tsx) records `registered` on confirmation and renders “going.” There is no proof from the ticket provider. This can inflate social proof, crew decisions, attendance metrics, and reminders. **Action:** make the status honest (`saved/interested`, `ticket link opened`, `I got tickets` self-report, and verified only where a provider integration exists). Show clearly where tickets live, retain the purchase link, and allow the person to correct their status. A native ticket wallet is a later decision, since JustGo currently aggregates external registration.

**3. Core event decision facts are incomplete in the live feed contract.** [`pivotQueries.ts`](../../Meridian-Mobile/src/services/api/pivotQueries.ts) lists title, description, location, start/end, external link, tags, and host. It declares a richer `details` object but notes that the backend is not sending it; [`pivotFeedService.js`](../backend/services/pivotFeedService.js) serializes the base fields without that object. The UI has a ticket detail component prepared for price, tiers, availability, and practical details, but real users may not see them. Before an external purchase, people reasonably need free/price range, fees or “see final price,” sold out/waitlist, age limit, doors versus start, address or map, accessibility, and cancellation policy when known. **Action:** make a minimum event information contract with provenance and “unknown” semantics; populate it in ingest/creator forms, enforce quality before publication for the highest-value fields, and show it on mobile and public web. Do not infer a price or availability from stale scraped text.

**4. The first-value path requires substantial commitment.** [`PivotAppNavigator.tsx`](../../Meridian-Mobile/src/pivot/navigation/PivotAppNavigator.tsx) routes unauthenticated people through city/auth; [`pivotOnboardingFlow.ts`](../../Meridian-Mobile/src/pivot/screens/onboarding/pivotOnboardingFlow.ts) has six steps (name, age, interests, calendar, theme, contacts) before the main app. Calendar and contacts can be skipped, but still occupy the sequence. The [public landing](../frontend/src/pages/JustGoLanding/JustGoLanding.jsx) presents a small deck and mostly iOS store CTAs; the public event page is informational and sends the visitor into the app. This is a high-friction path for someone following one event link or checking whether their city has enough events. **Action:** let visitors browse a useful city sample and open an event before account creation; defer calendar, theme, and contacts to the moment their benefit is clear. Keep age checks at the point required for access. Run a first-session test from shared event link to first useful event.

### P1 — meet common consumer expectations

**5. Explore offers little control for a person with a specific constraint.** [`PivotExploreScreen.tsx`](../../Meridian-Mobile/src/pivot/screens/PivotExploreScreen.tsx) hard-codes sort to `soonest`; the visible chips are mainly friends, tonight/day, and tags, while the API supports more than the UI exposes. Search and selected collection reset when re-entering Explore from the tab. Competitors routinely offer date range, distance/neighborhood, price/free, and event type filters ([Meetup](https://help.meetup.com/hc/en-us/articles/39235072484109-Finding-an-event), [Eventbrite](https://www.eventbrite.com/help/en-gb/articles/783059/how-to-use-the-eventbrite-iphone-app/)). **Action:** add a small “when/where/cost” filter sheet, visible sort choice, and preserve search/filter state across tab visits. Keep curated rails as the default.

**6. Saved plans lack a durable, obvious home.** JustGo has `interested` intent and a current-week [`PivotWeekPlansScreen.tsx`](../../Meridian-Mobile/src/pivot/screens/PivotWeekPlansScreen.tsx), plus recap in Week. It does not expose a clear Saved destination spanning future weeks and cities, nor does it visibly separate “I might go” from “I have a ticket.” [Eventbrite](https://www.eventbrite.com/consumer/eventbrite-app/) and [Meetup](https://help.meetup.com/hc/en-us/articles/39235072484109-Finding-an-event) make saved and attending events retrievable. **Action:** create a persistent Plans/Saved area with upcoming saved, self-reported/verified attendance, past, and removed events. Make save available from cards and detail without forcing a swipe session; preserve the weekly ritual as the home experience.

**7. Event changes and reminders are not yet a clear consumer service.** The backend sends weekly Drop and crew nudges, and the shared notification service has local preference fields. Yet [`PivotAccountSettingsScreen.tsx`](../../Meridian-Mobile/src/pivot/screens/PivotAccountSettingsScreen.tsx) has no notification controls; [`NotificationContext.tsx`](../../Meridian-Mobile/src/contexts/NotificationContext.tsx) registers push after authentication, which can trigger the OS permission prompt before a JustGo-specific explanation of value. There is no visible user journey for cancellation, time/venue change, sold-out/waitlist changes, or saved-event reminders. [Meetup](https://help.meetup.com/hc/en-us/articles/40708711818637-What-notifications-Meetup-can-send) has explicit event-change and saved-event updates. **Action:** introduce event revision alerts for saved/going users, a concise “why we ask for notifications” prompt at the first useful moment, and simple Drop/plan/social notification controls. Audit real delivery and deep-link destinations.

**8. Organizer affinity has no consumer loop.** Cards show `displayHost`, but the organizer is mostly text in the consumer flow, and the [identity plan](../../Meridian-Mintlify/strategy/just-go-organizer-identity-plan.mdx) explicitly excludes consumer follow and public host pages. Competitors let people follow organizers or artists and see future events ([Eventbrite](https://www.eventbrite.com/help/en-us/articles/161196/como-configurar-la-pagina-de-perfil-del-organizador/), [DICE](https://dice.fm/bundle/dooinit-festival-4mwr?lng=en-US)). **Action:** after organizer IDs are reliable, make host names tappable to a lightweight event history/upcoming page, then add follow plus restrained new-event alerts. This creates a repeat visit reason that does not depend on the weekly Drop alone.

**9. Account recovery and basic self-service are thin.** The JustGo auth screen offers email/password and social login, but no visible forgot/reset password route in the Pivot screens. Account settings provide interests, safety, legal/support, and deletion, while profile editing and notification preferences are absent. [Eventbrite’s app help](https://www.eventbrite.com/help/en-gb/articles/783059/how-to-use-the-eventbrite-iphone-app/) includes profile, location, and password management. **Action:** add password reset and a complete recovery test, basic profile editing, and notification controls. Check that social-login users see only relevant credential options.

**10. Public discovery is narrower than the app’s ambition.** Public event pages have good server generated Open Graph and structured event metadata in [`justGoSpaHtml.js`](../backend/utilities/justGoSpaHtml.js), and the landing has a small event deck. There is no public city browse/search catalog comparable to [Partiful Explore](https://partiful.com/explore) or [Fever city discovery](https://feverup.com/en). **Action:** create an indexable city/week page using the published catalog and conservative privacy rules, with filters and direct event pages. Keep the app as the personalized Drop and social planning destination. Measure search entry → event view → registration/store continuation.

**11. Creator operations are still heavily gated.** The [creator workspace](../frontend/src/pages/JustGoCreator/JustGoCreatorEventWorkspace.jsx) has event stats and editing for allowed states, but explicitly has no publish/cancel/delete controls because the API does not grant them. This is workable for a curated pilot and constrains supply growth, urgent correction, and cancellation communication. **Action:** first add a structured correction/cancellation request with clear service-level expectations and attendee impact; later delegate approved edits and cancellation to verified organizers with audit history. Preserve editorial review for discovery eligibility.

**12. Cross-channel acquisition measurement is a volume funnel, not a joined journey.** [`pivotAcquisitionFunnelService.js`](../backend/services/pivotAcquisitionFunnelService.js) says landing visitors are not joined to app users and that `session_start` is not recorded. The report can show useful stage volumes but cannot reliably attribute a share, public event view, install, signup, saved event, and ticket open to one campaign or event. **Action:** use privacy-safe campaign/event referral IDs and deferred deep-link continuity, then report event-share → page → install/open → event detail → save/ticket-open. Do not treat the current ratio of monthly visitor counts as a conversion rate.

**13. Users cannot flag an incorrect or unsafe listing from event detail.** [`PivotSafetyScreen.tsx`](../../Meridian-Mobile/src/pivot/screens/PivotSafetyScreen.tsx) handles reporting and blocking people, while event detail has share, ticket, calendar, and social actions but no event-report action. An aggregator needs a fast way to hear that a link is broken, an event was cancelled, a location is wrong, or the listing is unsafe. **Action:** add “Report a problem” on event detail and the public page with structured reasons, event ID, and a support response route. Feed frequent corrections back into source quality and release checks.

**14. The personalized Drop needs exposure safeguards before dense-city growth.** The [ranker vision](../../Meridian-Mintlify/strategy/just-go-drop-ranker-vision.mdx) makes organizer reach and city pulse depend on reserved exploration slots and candidate-level exposure logging. The [Drop honesty plan](../../Meridian-Mintlify/strategy/just-go-drop-honesty-plan.mdx) still marks those tasks pending, and no corresponding `drop_explore` or `exploreSlotCount` path appears in the current feed service. This is a supply-side growth gap: new or niche events can receive too few impressions to learn whether they fit. **Action:** complete the already specified exploration budget, exposure logs, and evaluation before optimizing on swipe rate alone. Use ticket-open/attendance as guardrails, as the strategy requires.

**15. Add a lightweight one-event coordination loop.** JustGo has strong crews and a substantial Decide flow, but a first-time visitor may only want to send one event to two friends and see a yes/maybe response. Partiful’s [link RSVP and visible guest interest](https://help.partiful.com/en-us/articles/15525594-why-use-partiful) show the value of a low-commitment loop. **Action:** test “send to friends” from event detail with a shared event thread or tiny poll before asking users to form a persistent crew. Keep recipient privacy and block controls from the existing Safety flow.

### P2 — targeted growth and polish

**16. Give users a reason to return after an event.** JustGo already has an event feedback prompt and friend/crew structure. A concise attended/not attended confirmation, optional rating, and next-event recommendation can improve both retention and ranking quality. [Meetup](https://help.meetup.com/hc/en-us/articles/40708711818637-What-notifications-Meetup-can-send) uses post-attendance nudges; [Partiful](https://help.partiful.com/en-us/articles/15525594-why-use-partiful) supports event photos. **Action:** measure completion of existing feedback first, then test one social or recommendation follow-up. Avoid building a public review system before volume and moderation are ready.

**17. Finish platform-specific acquisition and release checks.** The public event fallback offers Play links in [`justGoPublicEventAcquisition.js`](../frontend/src/pages/JustGoPublicEvent/justGoPublicEventAcquisition.js), while the main landing’s CTAs in [`JustGoLanding.jsx`](../frontend/src/pages/JustGoLanding/JustGoLanding.jsx) use only `JUSTGO_IOS_STORE_URL`. [`storeUrls.ts`](../../Meridian-Mobile/src/constants/storeUrls.ts) still falls back to the Meridian Go iOS listing if the JustGo URL environment variable is absent; [`JUSTGO_STANDALONE.md`](../../Meridian-Mobile/JUSTGO_STANDALONE.md) says Android Digital Asset Links fingerprints were placeholders at the time it was written. **Action:** verify the current deployed association files, store targets, and install-to-event return path on real devices; then make the landing platform-aware. The documentation may be stale, so this is a release verification item rather than a confirmed production defect.

## Social feature deep dive

**Assessment.** JustGo has a strong *group decision* core: friend requests and contact matching, friends interested/going on events, crew invites and share links, a weekly crew room, shortlist and ranked Decide, and friend/crew push destinations. The [crew social strategy](../../Meridian-Mintlify/strategy/just-go-crew-social-plan.mdx) rightly centers the weekly ritual. The missing layer is the everyday journey around that ritual: notice a person, invite them to one event, see their response, settle the practical plan, and stay connected afterward. This is where the product currently feels less social than the machinery underneath it.

**Discoverability finding and local fix.** The original first-circle prompt on Week said only “no circle yet” and “get started”; Profile exposed Friends but not Circles. The local card now leads with the problem it solves—turning “we should hang out” into a plan—and a “try it out” action. The next screen explains inviting friends, saving events each person likes, and choosing one outing together before naming a circle. Profile now has a Circles entry. This still needs a device walkthrough and a measure of card views → taps → circle created → first friend joined.

[`PivotEventFriendsSheet.tsx`](../../Meridian-Mobile/src/pivot/components/PivotEventFriendsSheet.tsx) and the crew roster render names as static rows. | Make identity rows lead to a compact profile/action sheet: shared crews or events, invite to this event, and relevant safety actions. Keep the profile sparse and consent-based; a full public social profile is unnecessary for this use case. **What to build first.** Verify the new leave flow, then ship mute and activity visibility before making social sharing more prominent. Then test one-event friend invitations with responses, followed by the post-Decide plan card. These are smaller and more directly tied to attendance than a general feed or full chat system. Measure event detail → friend invite sent → recipient open → response → ticket confirmation → attended, and circle join → first Decide → repeat Decide → leave/mute. The current [acquisition funnel service](../backend/services/pivotAcquisitionFunnelService.js) cannot join visitor and app journeys, so add privacy-safe invite attribution before reading those as conversion rates.

## Suggested sequence and measurement

1. **Fix the public event CTA** and test all installed/uninstalled browser states. This is a direct funnel defect with clear pass/fail behavior.
2. **Make event and attendance state trustworthy.** Ship the minimum fact contract, correct self-reported ticket status, and cancellation/change handling. Measure detail → external open → self-report and later verified attendance where possible.
3. **Reduce first-value friction.** Allow city/event browsing before signup, shorten first-run onboarding, add account recovery, and measure first useful event view and first save per new visitor.
4. **Build repeat utility.** Persistent Saved/Plans, practical Explore filters, event updates, and notification controls. Measure weekly retained users and saved → attended behavior, not just swipe interest.
5. **Build compounding loops.** Organizer pages/follows, public city browse, lightweight friend coordination, and joined share attribution. Evaluate these against event attendance and repeat visits.

Before a visual-design verdict, run a device walkthrough on small and large iPhones, Android, VoiceOver/TalkBack, large text, reduced motion, weak network, empty city, sold-out/cancelled event, and installed/uninstalled shared-link states. The current code includes some accessibility labels and reduced-motion handling, but this static audit cannot establish the rendered experience or actual touch-target sizes.
